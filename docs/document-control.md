# 项目交付文档总控

## 1. 作用
- 这是整个项目唯一的文档导航入口。
- 目标是用一个文档说清楚：每份文档是干什么的、应该写什么、什么时候更新、是否纳入最终提交。
- 当需求、设计、实现、测试变化时，先更新对应主来源文档，再回到这里更新状态，避免多份文档互相打架。

## 2. 文档分类

### 2.1 外部输入材料
- 这些是老师提供的材料，只作为需求来源保留在本地，不纳入最终提交包。
- 包括：
  - `2025-2026学年第2学期《人机交互技术及应用》课程大作业.doc`
  - `2025-2026学年第2学期《人机交互技术及应用》大作业评分标准.doc`
  - `期末考试说明.pptx`

### 2.2 内部过程文档
- 这些文档服务于开发、审计和范围控制。
- 默认保留在仓库中，但不放入给老师的最终提交包。

### 2.3 最终交付文档
- 这些文档直接服务于最终提交或最终报告编写。
- 在编码推进期间先维护 Markdown 底稿，最终再导出老师需要的 Word 报告和正式说明书。

### 2.4 仓库底稿与老师终稿的关系
- 仓库中的 `Markdown` 文档用于统一管理需求、设计、测试和报告素材，是开发阶段的主来源。
- 老师最终要求提交的是 `Word 版课程报告 + 源码工程 + 系统配置说明书 + 数据库 SQL`。
- 因此，仓库里允许存在“为最终交付服务但不直接交给老师”的底稿文档，例如：
  - `docs/course-report-outline.md`
  - `docs/assets/README.md`
  - `docs/test-report.md`
- 这类底稿文档的作用是防止信息散落；最终提交前应把其中内容回填到正式 `Word` 报告或正式说明书。

## 3. 使用规则
- 新增任何文档，先在这里登记。
- 每份文档必须说明：
  - 用途。
  - 必含内容。
  - 主来源主题。
  - 是否提交给老师。
  - 当前状态。
- 同一个主题只能有一个主来源文档，其它文档只做引用或摘要。

## 5. 最终提交包边界

### 5.1 应纳入最终提交包
- 源码目录：`app/`、`templates/`、`static/`、`run.py`、`requirements.txt`

- `.git/`
- `.gitignore`
- `.pytest_cache/`
- `__pycache__/`
- `*.pyc`
- 老师提供的源要求文档
- 内部过程文档：`docs/superpowers/...`、`docs/requirements-audit.md`、`docs/document-control.md`
- 仓库底稿：`docs/course-report-outline.md`、`docs/test-report.md`、`docs/assets/README.md`、`sql/README.md`

## 6. 冲突预防规则
- 功能范围变化：先改设计说明，再检查实施计划、要求审计、报告提纲。
- 页面结构与视觉策略变化：先改页面优化专项设计，再检查主设计说明、报告截图清单和后续开发计划。
- 页面优化进入编码前：先改页面优化实施计划，再执行模板、样式、脚本和测试改动。
- 路由、字段、表结构变化：先改代码和 `sql`，再改数据库说明、部署说明、报告草稿。
- 测试结果变化：先改测试记录，再同步到报告正文。
- 报告格式变化：先改报告提纲，再回写设计说明和总控文档中的状态。

## 7. 更新顺序
1. 需求变化时，先更新设计说明。
2. 再更新要求审计和实施计划。
3. 编码落地后，更新 `sql`、部署说明、数据库说明。
4. 测试完成后，更新测试记录。
5. 最后回填课程报告正文提纲和正式 Word 报告。
