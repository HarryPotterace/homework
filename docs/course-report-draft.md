# 智慧校园心理辅导与情绪感知交互子系统课程报告正文底稿

> 用途：本文件是提交给老师的 Word 报告正文底稿。正式提交前，将本文件内容结合截图、流程图、ER 图、类谱系树排版到老师模板中。

## 第一章 系统需求分析

### 1.1 系统需求
随着高校对学生心理健康工作的持续重视，传统依赖纸质问卷、线下登记和人工排班的管理方式逐渐暴露出响应慢、信息分散、匿名支持不足和统计展示不及时等问题。学生在面对心理压力、焦虑、低落等情绪时，往往不愿直接暴露身份，导致心理问题发现滞后。另一方面，咨询师和管理员需要同时处理测评记录、匿名反馈、预约安排和总体态势展示，若缺少统一系统，工作效率较低。

本项目面向“学生自助使用 + 咨询师后台处理 + 大屏脱敏展示”三类场景，设计并实现一个基于 B/S 架构的智慧校园心理辅导与情绪感知交互子系统。系统以学生移动端为主要交互入口，以后台端作为咨询师与管理员的工作平台，以大屏看板作为脱敏汇总展示终端，形成完整的业务闭环。

### 1.2 功能需求
系统功能围绕三端展开。

学生端需要支持注册、登录、个人资料维护、量表测评、匿名树洞、情绪感知交互、咨询预约和预约管理。其核心目标是降低学生使用门槛，提供更柔和、低打扰的心理支持入口。

后台端需要支持后台登录、统计总览、测评记录查看、匿名树洞查看、预约处理和基础账号区分。其核心目标是让咨询师和管理员能够在统一界面中快速掌握学生心理服务运行情况。

大屏端需要支持风险人数、情绪分布、测评趋势和预约热度等聚合结果展示，并确保不暴露学生姓名、学号和联系方式等身份信息。其核心目标是满足值班展示和总体态势观察需求。

### 1.3 性能需求
系统需要满足以下非功能要求：

- 页面交互流程清晰，学生端在手机宽度下可完整使用。
- 后台页面在桌面浏览器中表格与导航结构稳定。
- 大屏界面在 `1920x1080` 分辨率下具备可读性。
- 登录采用 Session 管理，学生端与后台端账户隔离。
- 树洞内容默认匿名，大屏仅展示脱敏聚合数据。
- 前端具备基础非空校验和密码强度校验，减轻无效提交。

## 第二章 可行性分析

### 2.1 技术可行性
本系统采用 `Flask + Jinja2 + Bootstrap + 自定义 CSS/JS + MySQL` 的单体 B/S 方案。该方案具有以下优势：

- 后端、页面模板和少量异步接口集中在一个工程中，适合课程作业在有限周期内完成完整交付。
- Flask 结构轻量，便于快速组织路由、服务、模型和测试。
- Jinja2 服务端渲染适合学生端、后台端和大屏端这类以表单、列表、统计展示为主的页面。
- MySQL 作为唯一运行数据库，便于解释表结构、输出 SQL 脚本并保持部署环境与课程交付环境一致。

与前后端完全分离方案相比，本系统不引入更重的工程复杂度，能在保证交互完整性的同时降低部署和演示门槛，更适合作为课程大作业交付。

### 2.2 操作可行性
学生端流程短，入口集中，用户可在较少页面跳转中完成登录、测评、树洞和预约。后台端采用统一菜单和分区列表，咨询师与管理员无需额外培训即可理解主要操作流程。大屏端只展示关键聚合数据，适合值班和汇报使用。

系统部署只依赖 Python、MySQL 和浏览器，环境要求明确，安装和验证过程可通过说明书快速复现，因此操作可行性较高。

### 2.3 可行性分析结论
综合技术实现难度、交互复杂度、部署成本和课程作业交付要求，本系统采用的技术路线和功能范围是可行的。规则式情绪感知虽然不属于训练型智能算法，但具备实现简单、逻辑透明、结果可解释的优点，符合课程作业对“交互设计 + 功能闭环 + 可说明性”的要求。

## 第三章 概要设计

### 3.1 系统设计原则
系统设计遵循以下原则：

- 亲和性：学生端采用更柔和的提示和较低压迫感的交互布局。
- 低打扰：情绪感知采用页面行为采集与文本规则推断，不要求用户额外佩戴设备或开启摄像头。
- 去标签化：树洞和情绪感知结果用于支持性反馈，不向学生贴上过强标签。
- 脱敏展示：大屏只展示聚合结果，不暴露身份数据。
- 可解释性：量表评分和情绪规则均采用显式规则，便于在报告中解释实现逻辑。

### 3.2 系统设计目标
系统目标是构建一个覆盖学生服务、后台管理和大屏展示的三端一体化心理辅导子系统，实现从学生自助使用、情绪提示、预约咨询到后台处理和大屏汇总的完整闭环。

### 3.3 系统总体架构
系统采用四层结构：

- 表现层：学生端页面、后台页面、大屏页面。
- 控制层：Flask 路由蓝图，包括 `student`、`admin`、`screen` 和 `api`。
- 业务层：量表评分、文本情绪推断、行为情绪推断、统计汇总等服务。
- 数据层：MySQL 持久化表和初始化 SQL 脚本。

表现层主要通过服务端渲染完成，少量 AJAX 接口用于行为采集、时段异步加载和看板数据读取，兼顾交互体验与工程简洁性。

### 3.4 系统流程设计
系统流程分为三条主线：

1. 学生进入系统后完成注册与登录，随后可以进行心理测评、匿名树洞、情绪感知交互和咨询预约。
2. 咨询师或管理员登录后台，查看测评记录、树洞信息和预约处理状态，并通过总览掌握整体运行情况。
3. 大屏端从聚合结果中读取学生总数、测评数、情绪分布和预约热度，输出脱敏展示结果。

对应流程图源文件见 `docs/assets/system-flow.md`，类谱系树源文件见 `docs/assets/class-tree.md`。

## 第四章 系统详细设计与实现

### 4.1 功能模块设计与实现

#### 4.1.1 用户注册模块
学生端注册页面包含学号、姓名、昵称、联系方式和密码字段。前端通过 `validation.js` 实现非空校验和密码强度校验，要求密码长度不少于 8 位，并包含字母和数字。后端在提交时再次校验学号唯一性，并使用密码哈希保存用户凭据。

#### 4.1.2 用户登录模块
学生端与后台端分别使用独立账号表。登录成功后，系统在 Session 中保存学生或后台身份信息，并在访问受保护页面时通过装饰器完成鉴权控制。这样既满足作业要求中的 Session 登录管理，也便于区分学生和咨询师/管理员访问边界。

#### 4.1.3 心理测评功能模块
系统内置 `PHQ-9` 和 `GAD-7` 两类量表。学生选择量表后，系统展示题目并接收作答结果。提交后，评分服务根据量表规则计算总分、等级和建议，再将结果写入 `assessment_records` 表。该实现既满足“测评选择、答题、得分、建议生成、记录保存”的业务要求，也为后台统计和大屏展示提供数据来源。

#### 4.1.4 情绪感知与自适应交互模块
系统的情绪感知模块由两个部分组成。

第一部分是树洞文本规则。系统对树洞正文进行关键词匹配，依据高风险词、低落词和焦虑词命中情况输出 `平静`、`焦虑`、`低落` 或 `需关注` 等结果，并给出风险等级。

第二部分是页面行为规则。前端在情绪感知页采集 `mousemove`、`click` 和 `keydown` 相关行为指标，并异步上报后端。后端根据鼠标速度、点击频次和停顿次数进行规则判断：高鼠标速度或高点击频次倾向于输出 `焦虑`，高停顿次数倾向于输出 `低落`，否则输出 `平静`。系统再根据结果切换 `default`、`gentle`、`calm-down` 等界面模式，实现提示文案、留白和交互氛围的自适应变化。

这种设计没有采用训练型机器学习模型，而是采用轻量可解释规则，优点是实现成本低、逻辑透明、适合课程作业答辩和说明。

#### 4.1.5 心理咨询预约功能模块
预约模块包含排班查看、预约创建、预约取消和后台处理四部分。学生端通过异步接口读取咨询师排班，当学生提交预约时，系统检查时段可用性，若可用则创建预约并锁定时段；若取消预约，则释放对应时段。后台端可查看全部预约记录并更新预约状态，形成完整的预约闭环。

#### 4.1.6 移动端响应式适配模块
学生端页面以手机访问为优先，布局采用纵向卡片结构，控制操作密度和点击目标尺寸。后台端以 PC 宽屏浏览为主，强调表格和导航。大屏端则以大字号指标、图表区域和信息块展示为主，强调远距离可读性。三端虽然共用一个后端工程，但在模板和布局上分别针对不同终端场景做了适配。

#### 4.1.7 方法与创新点
本系统的创新不在于复杂算法，而在于将人机交互设计与校园心理服务场景做了可落地的组合：

- 将学生端、后台端、大屏端整合到一个单体 B/S 系统中，降低开发和部署复杂度。
- 将树洞文本规则和行为规则结合，用轻量方式实现情绪感知反馈。
- 将情绪识别结果直接反馈到界面层，实现“状态感知 - 反馈提示 - 视觉调节”的交互闭环。
- 强调脱敏展示边界，使大屏看板只承担汇总展示，不承担身份识别功能。

### 4.2 数据库设计与实现

#### 4.2.1 系统 E-R 模型
数据库核心实体包括学生、后台账号、量表、量表题目、测评记录、树洞记录、行为日志、咨询师排班和预约记录。实体之间通过主外键建立关联，例如学生与测评记录、学生与预约、排班与预约之间均是一对多关系。

ER 图源文件见 `docs/assets/er-diagram.md`。

#### 4.2.2 数据库设计
本系统使用的主要数据表如下：

- `users`：学生注册信息。
- `admins`：后台账号信息。
- `scales` 与 `scale_questions`：量表及题目元数据。
- `assessment_records`：测评结果。
- `vent_posts`：匿名树洞记录。
- `behavior_logs`：交互行为采集记录。
- `counselors_schedule`：咨询师排班。
- `appointments`：预约记录。

数据库设计强调简单清晰和可演示性，详细字段说明见 `docs/database-design.md`，正式建表和初始化脚本见 `sql/schema.sql` 与 `sql/seed.sql`。

## 第五章 系统测试

### 5.1 系统测试

#### 5.1.1 测试任务
测试任务包括：

- 验证学生端主流程是否可用。
- 验证后台端与大屏端是否满足业务与脱敏要求。
- 验证量表评分、情绪规则和 SQL 资源是否可回归。
- 为最终课程报告整理功能、性能和兼容性证据。

#### 5.1.2 测试目标
系统测试目标包括功能正确、结果可解释、页面可访问和数据合规四个方面。其中功能正确性覆盖注册、登录、测评、树洞、情绪感知、预约、后台处理和大屏展示；数据合规重点检查匿名树洞和大屏脱敏展示。

#### 5.1.3 测试方案
自动化测试统一采用 `python -m pytest -q`。测试文件覆盖应用工厂、业务服务、学生路由、后台与大屏路由、SQL 资源以及后端现代化保护项。人工测试则按三端实际操作路径完成注册、测评、树洞、预约、后台查看和大屏检查。性能测试关注首页、大屏页和测评提交耗时。兼容性测试关注手机端、PC Chrome、PC Edge 和大屏环境。

### 5.2 测试结果及分析

#### 5.2.1 系统功能测试
截至 `2026-06-26`，三端关键页面优化采用工作树分支隔离开发并分别完成自动化验证。其中 `feat/student-ui` 分支执行 `python -m pytest -q` 结果为 `26 passed`，`feat/admin-screen` 分支执行同一命令结果为 `28 passed`。现有自动化测试已覆盖应用创建、量表评分、文本情绪规则、行为情绪规则、学生注册登录、学生首页支持入口、前端校验脚本加载、预约异步接口、测评结果保存、树洞情绪标签生成、预约创建与取消、后台工作台访问、大屏 KPI/图表渲染以及 SQL 资源存在性等内容。最终统一分支合并后仍需再执行一次总体验证并补充终端截图。

从覆盖结果看，系统核心业务主链路已具备较高稳定性。尤其是学生端注册登录、测评、树洞、预约和后台/大屏访问均已具备回归保障。

#### 5.2.2 系统性能测试
在本地开发环境下，使用 Flask 测试客户端对关键页面进行了重复请求测量。首页首次加载平均耗时约 `1.09 ms`，大屏页首屏渲染平均耗时约 `4.90 ms`，测评提交到结果展示平均耗时约 `44.20 ms`。说明在课程演示规模下，系统响应速度能够满足使用要求。

需要说明的是，这些数据属于本地环境性能基线，用于说明系统在当前部署规模下具有可接受响应时间，不等同于公网生产环境压测结果。

#### 5.2.3 兼容性测试
兼容性测试的目标环境为手机端 Chrome、PC Chrome、PC Edge 和 `1920x1080` 大屏。当前仓库已完成兼容性测试项与截图证据清单整理，但实机截图和最终记录仍需在最终演示环境中补齐。该部分对应的测试项和采集清单见 `docs/test-report.md` 与 `docs/assets/capture-checklist.md`。

#### 5.2.4 结果分析与评价
综合当前实现与测试结果，可以认为系统已经满足本课程大作业对三端架构、核心功能、Session 鉴权、前端校验、行为采集、预约异步接口和脱敏展示的主要要求。系统的优势在于结构清晰、实现完整、交互闭环明确、规则逻辑可解释，适合课程演示与答辩。

系统当前仍有两点局限。第一，情绪感知采用规则推断而非训练模型，适合演示与说明，但智能性有限。第二，最终提交前仍需补齐实机兼容性截图和 Word 排版版式，以完成最终交付闭环。

## 第六章 总结与展望

本项目围绕高校心理健康服务场景，完成了学生端、后台端和大屏端一体化的智慧校园心理辅导与情绪感知交互子系统设计与实现。系统通过测评、树洞、情绪感知和预约四类核心功能形成学生服务闭环，同时通过后台管理和大屏看板满足咨询师处理与总体展示需求。

在实现过程中，本项目没有追求重型算法，而是将课程的人机交互思想落到具体产品形态上：用更低门槛的学生端入口提升参与度，用规则式情绪反馈增强交互性，用脱敏大屏保障展示边界，用统一工程降低开发和部署复杂度。这种设计更符合课程作业“可实现、可解释、可展示”的目标。

后续若继续扩展，可考虑加入以下方向：

- 引入更细粒度的文本情绪分析模型。
- 增加语音或摄像头多模态情绪识别。
- 增加消息通知、咨询回访和风险预警机制。
- 对后台增加更丰富的筛选、导出和长期趋势分析功能。

需要明确的是，上述扩展方向均不属于本次课程大作业已实现范围。
